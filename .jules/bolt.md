## 2024-05-15 - OpenProject Cache Stampede
**Learning:** The `OpenProjectClient`'s naive `cached()` implementation triggers a cache stampede on startup or high concurrency because it didn't coalesce pending promises. Concurrent requests for `projects()`, `users()`, etc. executed identical API calls.
**Action:** When implementing application-level caching, always store the `Promise` of the work in progress rather than just the final result, preventing duplicate work while the first request is still inflight.
## 2024-05-18 - Eliminating N+1 Updates with CTEs in PostgreSQL
**Learning:** In the `database.ts` file, batch update operations like `supersedePendingProposalsForDeletedSource` were running an `UPDATE ... RETURNING` and then iterating over the results with a `for (const row of result.rows)` loop to fire individual `INSERT INTO task_audit_log` queries. Even though they were wrapped in `BEGIN`/`COMMIT` explicit transactions, this is an architectural anti-pattern (N+1 query problem) that adds unnecessary latency for every database roundtrip in the batch operation.
**Action:** When updating rows and subsequently inserting log/audit entries based on the results, always use a Common Table Expression (CTE) to combine the operations into a single round trip (e.g. `WITH updated AS (UPDATE ... RETURNING), inserted AS (INSERT ... SELECT ... FROM updated) SELECT * FROM updated`). This pattern also eliminates the need for explicit transaction blocks.
